# SQLite 복구 런북 작성 및 리허설 (#222)

- 상태: 계획 (착수 전)

> 이 문서는 **다음 작업 세션의 착수점**이다. 런북 본문이 아니다.
> 산출물은 `docs/guides/sqlite-restore-runbook.md`가 된다.

## 문제

`backup.ts`에 `runBackup`·`scheduleBackups`·`selectBackupsToPrune`은 있지만
**`restore` 함수도, 복구 런북도, 리허설 기록도 없다.**

[SQLite 컷오버 런북](../../guides/sqlite-cutover-runbook.md)은 **SQLite로 옮기는** 절차이지
`app-YYYYMMDD-HHmmss.db`를 되돌리는 절차가 아니다.

단일 인스턴스 + Railway 볼륨 위 임베디드 SQLite에서 이 백업은 논리 손상·잘못된
마이그레이션·실수 삭제에 대한 **유일한 방어선**이다. `app.db`가 깨진 순간
담당자에게 검증된 수순이 없으면 즉석 판단으로 프로덕션 DB를 만지게 된다.

## 성격

**엔지니어링보다 운영 문서 작업이다.** 자동 복구 API는 필요 없을 수 있다.
다만 **한 번은 실제로 해봐야** 한다 — 해보지 않은 절차는 인시던트 때 작동하지 않는다.

## 런북이 반드시 답해야 할 것

단순히 `.backup()` 덤프를 덮어쓰면 되는 게 아니다.

| 쟁점 | 확인해야 할 것 |
|---|---|
| **WAL/SHM** | `app.db-wal`·`app.db-shm`을 지우는가 남기는가. 남기면 복구본과 불일치한다 |
| **프로세스 정지** | 앱이 열고 있는 파일은 교체할 수 없다. Railway에서 어떻게 멈추고 되살리는가 |
| **부팅 시드** | `bootstrapSqlite`가 `seedCatalog`(빈 테이블일 때만)·`ensureCatalogEntries`를 돌린다. 복구본 상태에 따라 **무엇이 실행되는지** 확인해 명시 |
| **마이그레이션** | `runSqliteMigrations`가 복구본에 어떤 마이그레이션을 적용하는가(백업 시점이 과거 스키마일 수 있다) |
| **검증** | 무엇을 보고 "성공"이라 판단하는가 — 행 수, 최신 프로젝트, `/api/v1/health` |

## 작업 순서

1. 로컬에서 복구 리허설 — 백업 덤프 하나로 전체 수순을 실제로 밟는다
2. 위 표의 쟁점을 리허설 중 **실측**으로 답한다(추론하지 않는다)
3. `docs/guides/sqlite-restore-runbook.md` 작성 — 정지 → 파일 교체 → WAL 처리 → 기동 → 검증
4. **리허설 결과를 런북에 기록** (날짜·환경·실제로 걸린 부분)
5. `CLAUDE.md` 문서 참조 테이블에 등록
6. 자동화 필요 여부 판단 — 런북만으로 충분할 수 있다

## ✅ 결정 완료 (2026-07-30) — 산출물은 [복구 런북](../../guides/sqlite-restore-runbook.md)

사용자 결정: **프로덕션까지 리허설**. 로컬 리허설은 완료했고 런북에 실측값을 반영했다.
프로덕션 쓰기 리허설은 다운타임이 발생하므로 시간대 합의 후 수행한다.

리허설에서 나온 가장 중요한 발견: **이 서비스의 `app.db`는 4096B·테이블 0개이고
실데이터가 전부 WAL에 있다.** WAL만 지우면 DB가 사라지고, WAL을 남긴 채 백업본을 넣으면
복구가 조용히 무효화되는데 `integrity_check`는 `ok`를 반환한다.

아래는 착수 당시의 검토 내용이다.

## 사용자 판단 필요 ⚠️ (해소됨)

- **프로덕션 리허설 여부.** 로컬 리허설만으로 충분한가, Railway에서 한 번 밟아봐야 하는가.
  프로덕션 리허설은 실사용자 서비스에 다운타임을 만든다 — 사용자 승인 없이 진행하지 않는다.
