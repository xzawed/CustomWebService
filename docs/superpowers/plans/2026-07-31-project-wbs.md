### C1 재검토 결과 — "체크포인트 정책 부재"는 오진이었다 (2026-07-31)

최초 작성 시 "`wal_autocheckpoint` 설정이 없고 checkpoint 호출이 0건 = 정책 부재"로 적었으나,
**착수 전 전제를 실측해 보니 틀렸다.**

| 항목 | 실측값 |
|---|---|
| `wal_autocheckpoint` | **1000 페이지** (SQLite 기본값이 그대로 적용 중) |
| `page_size` | 4096 |
| → 체크포인트 임계 크기 | **약 3.91 MB** |
| 프로덕션 `app.db-wal` | **1.42 MB (~364 페이지)** |

즉 **정책은 살아 있고, 쓰기량이 적어 아직 발동할 이유가 없었을 뿐**이다.
"명시적으로 설정하지 않음"과 "정책이 없음"을 혼동한 것이다.

`app.db`가 6월부터 4096B인 2차 요인도 확인됐다: **종료 시 `raw.close()`를 부르는 경로가 없다.**
정상 종료는 체크포인트 후 WAL을 삭제하지만 Railway 재배포는 SIGKILL이라, WAL이 재시작을 넘어 계속 살아남는다.

**그래서 코드를 바꾸지 않기로 했다:**

- `raw.backup()`이 미체크포인트 WAL 프레임까지 담는 것이 이미 실측 확인됐다 → **백업은 원래 안전하다**
- 복구 절차(app.db 교체 + WAL/SHM 제거)는 2026-07-31 프로덕션 리허설로 검증됐다
- 공격적 체크포인트(임계 하향·주기 `TRUNCATE`)는 쓰기 증폭과 새 백그라운드 writer를 만들고,
  동시 리더가 있으면 블로킹된다 — **이미 측정으로 사라진 문제에 대한 해법이다**
- 오히려 "main 파일만 있으면 된다"는 **잘못된 안심**을 만들 수 있다. 이 서비스의 런북이
  올바른 이유는 정확히 main이 비어 있을 수 있기 때문이다

> **남는 실질 위험은 체크포인트가 아니라 두 가지다**: ① 사람이 `app.db-wal`을 "로그처럼 보여서"
> 지우는 실수(런북이 다루고 있다) ② **C2 오프-볼륨 DR 부재**(백업이 같은 볼륨에 있다).
> C1에 시간을 쓰는 대신 **C2가 실제 잔여 위험**이다.

선택적 위생 작업으로 남겨 두는 것(권장하지 않음, 필요해지면):
`runBackup` 성공 직후 같은 연결에서 `PRAGMA wal_checkpoint(PASSIVE)` 1회 —
새 스케줄러 없이 기존 24h 주기에 얹는 형태. 종료 시 `raw.close()` 추가도 마찬가지로 선택적이다.

### ⚠️ P3에서 드러난 것 — "레이스 수정"이라는 진단 자체가 틀렸다 (2026-08-01)

P3를 구현한 뒤 **적대적 검증(4개 렌즈)**을 돌린 결과, 고치려던 레이스가
**실제 브라우저에서 도달 불가**임이 런타임 프로브로 확인됐다.

- 폴링을 시작하는 지점은 3곳(visibility / stream_ended / stream_error)뿐이고 **전부 리더 루프 종료 후**다
- `reader.cancel()`은 **대기 중인 `read()`를 `{done:true}`로 즉시 종료**시킨다(프로브로 확인).
  따라서 visibility가 cancel한 뒤에 버퍼된 SSE `complete`를 처리하는 순서는 성립하지 않는다
- 즉 **abort가 취소할 "살아 있는 폴링"이 프로덕션에 존재하지 않는다**

그 순서가 성립하는 곳은 `cancel`을 무력화한 **테스트 목뿐**이었다.

#### 사용자가 실제로 겪던 원인: 폴링 예산 부족

| 항목 | 값 |
|---|---|
| 클라이언트 폴링 예산 | 120회 × 1초 = **120초** |
| 서버 파이프라인 예산 | `PIPELINE_MAX_DURATION_MS` 기본 **290초** |
| 간극 | **170초** |

모바일 백그라운드 전환 → 폴링 핸드오프 → **t≈120초에 클라이언트가 포기하고
`failGeneration('생성 시간이 초과되었습니다')`** → t≈200초에 서버는 정상 완료.
사용자는 **성공한 생성을 실패로 본다.** 이 경로에는 SSE가 이미 죽어 있어 abort도 래치도 개입하지 못한다.

→ `pollGenerationStatus`와 `RePromptPanel` 양쪽의 예산을 **300초**로 올렸다(서버 290초 + 마진).

#### P3의 실제 값어치

레이스 수정이 아니라 **"abort 후 terminal 콜백 금지" 방어적 불변조건 + 세션 컨트롤러 배선의
선행 작업**이다. 가드 배치 자체는 모든 await 경계를 빠짐없이 덮어 논리적 구멍이 없다.
**그 이름으로만 유지할 것** — 과장된 주석은 전부 정정했다.

**설계 원칙 (협의로 확정)**

- 추출 단위는 **커스텀 훅이 아니라 `src/lib/generation/` 아래 순수 DI 함수**다.
  잡으려는 버그가 렌더가 아니라 **순서·종료 경합**이므로, `pollGenerationStatus` 선례를 따른다
- **페이지에 남는 것**: `useRouter`·JSX·빌더 스텝 상태가 필요한 모든 것.
  **나가는 것**: `fetch` + 스트림 + 콜백만 필요한 모든 것
- **P1에서 동작을 고치지 않는다.** 기계적 이동 버그와 의도적 동작 변경을 같은 커밋에 섞으면
  안전망 없는 경로에서 원인을 가릴 수 없다
- **복잡도 48 → 15 미만은 단일 추출로는 안 된다.** 스트림 단위를
  `appendAndParseSse` / `dispatchSseEvent` / 루프로 더 쪼개야 한다
- `builder/page.tsx:323`(연관성 게이트, 복잡도 21)은 **별개 작업**이다 — 여기 묶지 말 것

### F7 재검토 결과 — Slack 경보는 붙이지 않는다 (2026-07-31)

sink가 살아났으니 착수 가능하다고 적었으나, **두 경로를 실제로 읽어 보니 경보 대상이 아니었다.**

| 경로 | 침묵 시 사용자 영향 | 결론 |
|------|-------------------|------|
| 배포 환불 실패 (`deploy/route.ts`) | 이미 실패한 배포 건에 대해 **하루치 슬롯 1개**를 잃는다. 다음 날 자동 회복 | **Slack ❌** — 이미 실패한 경로의 2차 증상에 경보를 다는 꼴 |
| 이벤트 persist 실패 (`eventPersister.ts`) | 감사 로그 행 하나 누락. 제품은 정상 동작 | **Slack ❌** — 생성 1건당 다수 이벤트가 발행되므로 **경보 폭풍** 위험 |

`SqliteEventRepository.persist()`가 **이미 내부에서 catch·warn하고 rethrow하지 않으므로**,
`eventPersister`의 catch는 사실상 도달하지 않는다(이중 best-effort). 설계 의도대로다.

**대신 진짜 결함을 하나 찾아 고쳤다**: `deploy/route.ts`의 환불이 `.catch(() => {})`로
**에러를 통째로 버리고 있었다.** 주석은 "generate의 보상 패턴과 동일"이라고 적혀 있었지만
generate 경로(`RateLimitService.decrementDailyLimit`)는 `logger.warn`을 남긴다 —
**주석이 사실과 달랐고 동작은 더 나빴다.** 삼키되 기록은 남기도록 고치고 회귀 테스트를 붙였다.

> **만약 나중에 정말 집계가 필요해지면** 스케줄러의 "상태 전이" 패턴이 아니라
> `errorRateMonitor`의 **전역 윈도 + 임계 1회 경보**를 복제할 것. 사용자·프로젝트 키의 Map을
> 만들면 무한 증가하거나, 이 프로젝트가 금지한 "활성 윈도 evict" 함정에 빠진다.
