### B3 선행조건 — env를 넣어도 API는 켜지지 않는다 (2026-08-04 실측)

B3(a)를 "무료 키 발급 → env 등록"으로만 적어 두었는데, **그것만으로는 사용자에게 아무 변화가 없다.**
착수 전에 코드를 전수로 확인한 결과:

| 확인한 것 | 결과 |
|---|---|
| `is_active`를 `true`로 **쓰는** 코드 | `ensureCatalogEntries`의 **Dog API·Lorem Picsum 하드코딩 정정뿐** |
| `is_active`를 토글하는 관리자 엔드포인트 | **없다** (admin 라우트 9종 전부 GET/POST 조회·검증용) |
| `keys-verify` / `verify-catalog` | `findMany({ isActive: true })` — **활성 API만 조회한다.** 비활성 API는 키를 넣어도 검증 대상에 들어오지 않는다 |
| `verify-catalog`가 쓰는 컬럼 | `verificationStatus`뿐. `is_active`는 건드리지 않는다 |

즉 비활성 25개는 **env를 등록해도 카탈로그·추천·프록시에서 계속 빠진다.**
`findMany`의 기본 필터가 `is_active=true AND deprecated_at IS NULL`이기 때문이다.

**그러므로 B3(a)는 오너 액션 + 코드 작업이 함께 필요했다:**

### ✅ 코드 쪽 선행조건은 해소됐다 (2026-08-04)

- `GET /api/v1/admin/keys-verify?includeInactive=true` — **비활성 API도 검증 대상에 넣는다.**
  기본값(활성만)으로는 새로 키를 넣은 대상이 정의상 비활성이라 확인할 방법이 아예 없었다.
  응답 `summary.activatable`이 "비활성인데 키가 실제로 먹히는" id 목록이다.
- `POST /api/v1/admin/catalog/activate` — **라이브 키 검증을 통과한 것만** `is_active=true`로 올린다.
  `{ dryRun: true }`로 무엇이 켜질지 먼저 볼 수 있고, `apiIds`로 대상을 좁힐 수 있다.

**검증 통과를 활성화의 전제로 못박은 이유**: 관리자가 손으로 켜게 두면 키가 틀린 API가
사용자에게 노출돼 401만 반환한다 — 2026-06-21에 정확히 그 상태로 7개가 방치됐던 이력이 있다.
뮤테이션 테스트로 이 가드가 실제로 막는 것을 확인했다.

**남은 것은 순수하게 오너 액션(무료 키 발급)뿐이다.**

> 원래 이 절은 "키만 넣으면 된다"는 잘못된 안내를 막으려고 썼다. 이제 절차가 완결됐으므로
> 위 2단계(등록 → `keys-verify?includeInactive=true` → `activate`)를 그대로 따르면 된다.

### C1 재검토 결과 — "체크포인트 정책 부재"는 오진이었다 (2026-07-31)

최초 작성 시 "`wal_autocheckpoint` 설정이 없고 checkpoint 호출이 0건 = 정책 부재"로 적었으나,
**착수 전 전제를 실측해 보니 틀렸다.**

| 항목 | 실측값 |
|---|---|
| `wal_autocheckpoint` | **1000 페이지** (SQLite 기본값이 그대로 적용 중) |
| `page_size` | 4096 |
| → 체크포인트 임계 크기 | **약 3.91 MB** |
| 프로덕션 `app.db-wal` (재검토 당시) | **1.42 MB (~364 페이지)** — 시점 관측, 불변조건 아님 |

즉 **정책은 살아 있고, 쓰기량이 적어 아직 발동할 이유가 없었을 뿐**이다.
"명시적으로 설정하지 않음"과 "정책이 없음"을 혼동한 것이다.

리허설 전(2026-07-30) 관측으로 `app.db`가 오래 4096B였던 2차 요인도 확인됐다: **종료 시 `raw.close()`를 부르는 경로가 없다.**
정상 종료는 체크포인트 후 WAL을 삭제하지만 Railway 재배포는 SIGKILL이라, WAL이 재시작을 넘어 살아남을 수 있다.
(2026-07-31 `.backup()` 복구 리허설 이후 프로덕션은 fat-main/empty-WAL 형태 — **크기는 시점 관측**.)

**그래서 코드를 바꾸지 않기로 했다:**

- `raw.backup()`이 미체크포인트 WAL 프레임까지 담는 것이 이미 실측 확인됐다 → **백업은 원래 안전하다**
- 복구 절차(app.db 교체 + WAL/SHM 제거)는 2026-07-31 프로덕션 리허설로 검증됐다
- 공격적 체크포인트(임계 하향·주기 `TRUNCATE`)는 쓰기 증폭과 새 백그라운드 writer를 만들고,
  동시 리더가 있으면 블로킹된다 — **이미 측정으로 사라진 문제에 대한 해법이다**
- 오히려 "지금 main이 크니 WAL은 무시해도 된다"는 **잘못된 안심**을 만들 수 있다. 런북이
  올바른 이유는 체크포인트 전 커밋이 `-wal`에만 있을 수 있기 때문이다

> **남는 실질 위험은 체크포인트가 아니다**: 사람이 `app.db-wal`을 "로그처럼 보여서" 지우는 실수
> (런북이 다루고 있다). on-volume `.backup()`은 그 논리 손상 축을 막는다.
> **볼륨 자체 손실 + 오프라인 사본 없음 → 복구 절차 없음**은 별 축이다. 유료 오프-볼륨 DR은
> **제외(2026-08-01)**로 닫혔고, 유일한 무료 오프-볼륨 경로는 사람이 `admin/backup/latest`를
> 당기는 선택 습관뿐이다 — **미완 구현 과제로 승격하지 말 것.** C1에 시간을 쓰지 말 것.

선택적 위생 작업으로 남겨 두는 것(권장하지 않음, 필요해지면):
`runBackup` 성공 직후 같은 연결에서 `PRAGMA wal_checkpoint(PASSIVE)` 1회 —
새 스케줄러 없이 기존 24h 주기에 얹는 형태. 종료 시 `raw.close()` 추가도 마찬가지로 선택적이다.

### C8 구현 결과 — 자동 PR이 아니라 이슈다 (2026-08-03)

`pnpm countries:check`가 업스트림을 받아 같은 변환을 돌리고 번들과 **바이트 단위로 비교**한다.
쓰기는 하지 않고 종료 코드로만 말한다: `0` 동일 · `1` 드리프트 · `2` 업스트림 도달 실패.

**`2`를 `1`과 분리한 것이 핵심이다.** 같은 코드였다면 GitHub raw의 일시 장애가
"데이터가 바뀌었다"로 둔갑해 헛된 알림을 만든다 — 월 1회짜리 신호가 신뢰를 잃는 가장 빠른 길이다.

**자동 갱신 PR을 만들지 않기로 했다.** 두 가지가 실측으로 막았다:

| 이유 | 실측 |
|---|---|
| 레포 설정이 Actions의 PR 생성을 막고 있다 | `gh api repos/.../actions/permissions/workflow` → `can_approve_pull_request_reviews: false` |
| 설정을 켜도 **`GITHUB_TOKEN`이 만든 PR에는 CI가 돌지 않는다** | GitHub의 재귀 실행 차단. 데이터 교체를 검증할 유일한 안전망이 사라진다 |

두 번째가 결정적이다. 자동 PR은 편해 보이지만 **검증되지 않은 데이터 교체**를 만든다.
사람이 `pnpm countries:generate` 후 평소대로 PR을 올리면 CI가 정상 동작한다.
그래서 워크플로는 드리프트일 때 **이슈 1건**만 열고, 이미 열려 있으면 중복 생성하지 않는다
(검색 인덱스는 반영이 늦어 중복을 만들 수 있으므로 REST 목록으로 즉시 판정한다).

**도입 즉시 값을 했다**: 첫 실행에서 시에라리온 통화 코드가 `SLL`→`SLE`로 바뀐 것을 잡았다.
번들 데이터는 그만큼 오래 stale이었고, 검사 수단이 없어 아무도 몰랐다.

> ⚠️ **Windows 함정 기록**: 최초 구현은 `process.exit()`로 코드를 반환했는데,
> `fetch`(undici) 핸들이 살아 있는 동안 강제 종료하면 libuv 어서션(`UV_HANDLE_CLOSING`)으로
> 죽으면서 **종료 코드가 127로 뭉개졌다**. 워크플로가 코드로 분기하므로 치명적이다.
> `process.exitCode`만 세팅하고 자연 종료시킨다. 합성 검증만 했으면 못 잡았을 결함이다.

### A6 결과 — 죽은 플래그를 배선하지 않고 **쓸모 있는 것으로 교체**했다 (2026-08-04)

오너 지시는 "안 쓰지만 **쓰면 좋은 부분이라면** 반영"이었다. 7행을 실제로 열어 보니
**배선할 가치가 있는 것이 하나도 없었다**:

| 플래그 | 실태 |
|---|---|
| `enable_ollama_fallback` | Ollama 코드가 저장소에 **0건**. 존재하지 않는 기능 |
| `enable_team_features` | 팀/조직 UI 없음 |
| `enable_advanced_prompt` | 해당 UI 없음 |
| `enable_multi_language` | 오너가 **계획 없음으로 종결**(A7) |
| `enable_code_viewer` · `enable_dark_mode` | 이미 무조건 켜져 있는 UI. 플래그를 읽는 곳 없음 |
| `enable_template_system` | **`false`인데 템플릿 시스템은 실제로 돌고 있다** — 값이 현실과 정반대 |

마지막 행이 결정적이다. 그대로 두면 언젠가 누군가 그 값을 믿고 배선해 **동작하는 기능을 끈다.**

**그래서 배선 대상을 바꿨다.** 이 테이블의 유일한 실질 가치는 "env와 달리 **재배포 없이
즉시 반영**된다"는 것이고, 그건 기능 구성이 아니라 **인시던트 대응 킬스위치**에 쓸모가 있다.
env를 바꾸면 Railway 재배포(+Wait for CI)가 필요하고 그동안 비용은 계속 나간다.

| 플래그 | 무엇을 막나 |
|---|---|
| `enable_generation` | AI 생성·재생성 즉시 중단 (비용 폭주·업스트림 장애) |
| `enable_signup` | 신규 가입만 차단 (남용). 기존 사용자 이용에는 영향 없음 |

**설계 규칙 3가지**(깨면 조용히 사고 난다):

1. **fail-open** — 행이 없거나 DB 읽기가 실패하면 **켜진 것으로 본다.** 이 스위치의 목적은
   의도적으로 *끄는* 것이지 켜는 게 아니다. DB 순간 장애가 서비스 중단으로 번지면
   스위치가 없느니만 못하다
2. **쿼터 증가 이전에 검사** — 꺼져 있는데 일일 한도만 깎이면 스위치를 올린 뒤에도 사용자가 못 쓴다
3. **`ensureFeatureFlags`는 기존 행의 `enabled`를 덮어쓰지 않는다** — 덮어쓰면 재배포가
   오너가 내린 킬스위치를 조용히 되돌린다. 화이트리스트 밖 행만 지운다

10초 인프로세스 캐시를 쓰며, **그 TTL이 곧 "스위치를 내린 뒤 실제로 멈추기까지의 최대 지연"** 이다.
쓰기 시에는 캐시를 즉시 버린다.

### C9 판정 — "미적용"이 아니라 **적용할 수 없는 구조**다 (2026-08-04)

WBS는 이것을 "재생성 경로에 미적용 · S · 의도 확인 선행"으로 적어 두었다.
착수 전 실측하니 **전제가 틀렸다.**

| 확인한 것 | 결과 |
|---|---|
| `projects` 테이블에 template 컬럼 | **없다** |
| `templateId`를 저장하는 코드 경로 (services·repositories·lib/ai 전수) | **0건** |
| `regenerateSchema` | `projectId` + `feedback`뿐 |

`templateId`는 빌더의 클라이언트 상태(`contextStore`)로만 존재하고, 최초 생성 요청에서
`buildStage1SystemPrompt(templateHint)`에 한 번 쓰이고 사라진다. **재생성 시점에는 그 값이
어디에도 없다.** 따라서 "재생성에도 적용"은 코드 한 줄이 아니라 **컬럼 추가 + 마이그레이션**이
필요한 작업이고, S 크기 위생 작업이 아니다.

**그리고 적용하는 것이 옳은지도 자명하지 않다.** 재생성은 *기존 코드 + 사용자 피드백*으로
고쳐 쓰는 흐름이다(`buildStage1RegenerationUserPrompt(previousCode, feedback, ...)`).
템플릿 힌트는 **처음에 뼈대를 세우는 스캐폴드**이고, 그 뼈대는 이미 고쳐 쓸 코드 안에 들어 있다.
다시 주입하면 "대시보드 말고 갤러리로 바꿔줘" 같은 피드백과 **정면으로 충돌**할 수 있다.

→ **의도된 설계로 종결한다.** 나중에 "템플릿이 재생성까지 구속해야 한다"는 제품 판단이 서면,
그때는 위생 작업이 아니라 `projects.template_id` 영속화 + 충돌 규칙 설계로 시작해야 한다.

### ⚠️ P3에서 드러난 것 — "레이스 수정"이라는 진단 자체가 틀렸다 (2026-08-01)

P3를 구현한 뒤 **적대적 검증(4개 렌즈)**을 돌린 결과, 고치려던 레이스가
**실제 브라우저에서 도달 불가**임이 런타임 프로브로 확인됐다.

- 폴링을 시작하는 지점은 3곳(visibility / stream_ended / stream_error)뿐이고 **전부 리더 루프 종료 후**다
- `reader.cancel()`은 **대기 중인 `read()`를 `{done:true}`로 즉시 종료**시킨다(프로브로 확인).
  따라서 visibility가 cancel한 뒤에 버퍼된 SSE `complete`를 처리하는 순서는 성립하지 않는다
- 즉 **abort가 취소할 "살아 있는 폴링"이 프로덕션에 존재하지 않는다**

그 순서가 성립하는 곳은 `cancel`을 무력화한 **테스트 목뿐**이었다.

#### 사용자가 실제로 겪던 원인: 폴링 예산 부족

| 항목 | 값 |
|---|---|
| 클라이언트 폴링 예산 | 120회 × 1초 = **120초** |
| 서버 파이프라인 예산 | `PIPELINE_MAX_DURATION_MS` 기본 **290초** |
| 간극 | **170초** |

모바일 백그라운드 전환 → 폴링 핸드오프 → **t≈120초에 클라이언트가 포기하고
`failGeneration('생성 시간이 초과되었습니다')`** → t≈200초에 서버는 정상 완료.
사용자는 **성공한 생성을 실패로 본다.** 이 경로에는 SSE가 이미 죽어 있어 abort도 래치도 개입하지 못한다.

→ `pollGenerationStatus`와 `RePromptPanel` 양쪽의 예산을 **300초**로 올렸다(서버 290초 + 마진).

#### P3의 실제 값어치

레이스 수정이 아니라 **"abort 후 terminal 콜백 금지" 방어적 불변조건 + 세션 컨트롤러 배선의
선행 작업**이다. 가드 배치 자체는 모든 await 경계를 빠짐없이 덮어 논리적 구멍이 없다.
**그 이름으로만 유지할 것** — 과장된 주석은 전부 정정했다.

**설계 원칙 (협의로 확정)**

- 추출 단위는 **커스텀 훅이 아니라 `src/lib/generation/` 아래 순수 DI 함수**다.
  잡으려는 버그가 렌더가 아니라 **순서·종료 경합**이므로, `pollGenerationStatus` 선례를 따른다
- **페이지에 남는 것**: `useRouter`·JSX·빌더 스텝 상태가 필요한 모든 것.
  **나가는 것**: `fetch` + 스트림 + 콜백만 필요한 모든 것
- **P1에서 동작을 고치지 않는다.** 기계적 이동 버그와 의도적 동작 변경을 같은 커밋에 섞으면
  안전망 없는 경로에서 원인을 가릴 수 없다
- **복잡도 48 → 15 미만은 단일 추출로는 안 된다.** 스트림 단위를
  `appendAndParseSse` / `dispatchSseEvent` / 루프로 더 쪼개야 한다
  — **실제로 그 목표까지는 가지 않았다**(위 실측표: 25·24로 분산). 더 쪼갤지는 별도 판단
- 연관성 게이트(복잡도 21)는 **별개 작업**이다 — 여기 묶지 말 것.
  추출로 줄이 밀려 위치가 `page.tsx:323` → **`page.tsx:218`**로 바뀌었다(2026-08-01 실측)

### F16 — `.claude/rules/` 이관은 "금지"가 아니라 "관측 대기"다 (2026-08-06)

### F14 진행 — `promptBuilder.ts`는 복잡도가 아니라 **로직/콘텐츠 혼재** 문제였다 (2026-08-05)

착수 전 실측이 작업의 성격을 바꿨다. 1437줄 중 **약 1030줄이 정적 프롬프트 텍스트**였고,
실제 로직은 ~400줄뿐이었다. SonarCloud `S3776` 상위 10위에 이 파일이 없던 이유가 이것이다 —
**복잡도 문제가 아니다.** `showError`·`openModal`·`setButtonLoading`·`showToast`처럼 함수로
보이던 것들도 전부 **프롬프트 문자열 안에 박힌 예시 JS**였다.

그래서 값어치는 "복잡도 감소"가 아니라 **분리**에 있다. 결과:

| 파일 | 줄수 | 역할 |
|---|---:|---|
| `promptBuilder.ts` | **384** (was 1437) | 로직 + 캐싱 + 9개 export 빌더 |
| `prompts/stage1System.ts` | 806 | 텍스트 전용 |
| `prompts/stage2System.ts` | 223 | 텍스트 전용 |
| `prompts/stage2FunctionSystem.ts` | 35 | 텍스트 전용 |

**안전망은 일회성 등가성 검증이었다 — 영구 해시 테스트를 만들지 않았다.**
프롬프트는 앞으로도 계속 튜닝될 대상이라, 해시를 테스트에 박으면 **의도적 수정마다 깨져서
"해시만 갱신하는 의식"** 이 생긴다. 그건 아무것도 지키지 않으면서 신뢰만 깎는 테스트다
(E10에서 걷어낸 무단언 테스트와 같은 부류). 대신 리팩터링 전에 9개 빌더의 출력을
21개 케이스(캐시 경로·`clearPromptCache` 후 재생성 경로 포함)로 덤프해 두고,
리팩터링 후 **sha256 + 파일 단위 바이트 비교로 전부 동일함을 확인**한 뒤 하네스를 버렸다.

> ⚠️ **소스가 CRLF다.** 템플릿 리터럴 안의 줄바꿈이 곧 프롬프트 내용이므로, 텍스트를
> 옮길 때 개행을 정규화하면 **모델이 받는 문자열이 조용히 바뀐다.** 등가성 검증이 없었다면
> 눈으로는 절대 못 잡는다.

**설계**: 새 모듈은 **캐시 없는 순수 함수**이고 캐시는 `promptBuilder.ts`에 남겼다.
덕분에 세 개의 `let cached…`가 상단에 모였고, 선언이 1300줄 떨어져 있어서 달려 있던
`"declared further below; accessible via closure at call time"` 변명 주석이 사라졌다.

> (검사기 주석의 한계 (b)). 그래서 **해소 서술에는 행 번호를 새로 쓰지 않는다** — 심볼명으로 쓴다.

**해소 방식(2026-08-07)**: 결함 2·5는 **소유권 토큰**으로 닫았다 — 해제 조건을 *"내 요청이
취소됐나"*(`!signal.aborted`)에서 *"내가 아직 최신 소유자인가"*(`reqIdRef.current === reqId`)로
바꿨다. 전자는 (a) 후속 요청의 선점과 (b) 리셋에 의한 폐기를 구분하지 못하는데, (a)에서는
끄면 안 되고 (b)에서는 반드시 꺼야 한다. **한 비트로 두 질문에 답하려던 것이 결함이었다.**
결함 1은 `regen: { projectId, version } | null`로 **신원을 값 안에 담아** 리셋 호출 자체를
불필요하게 만들었다 — 리셋 누락이 버그가 될 수 없는 형태다.

> **왜 abort 지점마다 해제 코드를 넣지 않았나**: 그 방식은 의무가 `abort 지점 × 플래그`로
> 곱해진다. **#289가 정확히 그 곱셈을 절반만 채우다 결함 5를 만들었다.** 같은 형태를 한 번 더
> 사는 것은 "최소 수정이 재발을 못 막았다"는 전제와 모순된다.

### 결함 6 정정 (2026-08-08) — 절반은 사실이 아니었고, 그 절반을 테스트가 green으로 고정했다

**가입은 기술대로였다.** `fetch`는 네트워크 실패에 정말로 reject하므로 `setLoading(true)` 고착이
실재했다 — [#292](https://github.com/xzawed/CustomWebService/pull/292)가 맞게 닫았다.

**로그인은 재현되지 않았다.** `next-auth@5.0.0-beta.32`의 `signIn()`은 **네트워크 실패에 throw하지
않는다** — 내부 `fetchData`가 모든 예외를 삼켜 `null`을 반환하고, 그 결과 `signIn`은 **`undefined`로
resolve**한다(실측). 따라서 #292가 추가한 `try/catch`는 **도달하지 않는 코드**였고, 원본 코드는
`res?.error`가 `undefined`라 그대로 통과해 **미인증 상태로 `/dashboard`에 이동했다가 튕겨 나왔다** —
"버튼 고착"이 아니라 **"아무 설명 없이 로그인 화면으로 되돌아옴"** 이 실제 증상이다.

> **가장 나쁜 부분은 결함이 아니라 테스트다.** #292는 `mockRejectedValue`로 *"throw한다"* 는
> **거짓 전제를 단언으로 고정**했다. 초록색이었고, 그래서 아무도 다시 묻지 않았다.
> 이 항목이 G1(증거 등급)의 실증 사례다 — 라이브러리 동작을 **읽지 않고 추정**했다.

→ [#300](https://github.com/xzawed/CustomWebService/pull/300)이 `!res` 분기로 닫고, 테스트를
`mockResolvedValue(undefined)`(실제 경로) + 좁은 `TypeError` 경로 + **문구 대조 통제군**으로 교체했다.

**남긴 것(부풀리지 않고 명시)**:
- `isLoadingCatalog`(144행)의 `!aborted` — abort 주체가 언마운트뿐이라 도달 불가. 일관성 결여만 남음
- `isSuggestionsLoading` — 상태는 고쳐졌으나 **오늘 화면에 드러나는 경로를 찾지 못했다**(없다고
  증명한 것은 아니다). 회귀 테스트 없음 — "증상이 고쳐졌다"고 보고하면 안 된다

**선행 조건(완료)**: 이 페이지가 커버리지 집계에서 빠져 있었다 → `vitest.config.ts` 편입
