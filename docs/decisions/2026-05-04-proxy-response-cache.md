# ADR: 프록시 응답 캐시 — LRU+TTL 인메모리 캐시 도입 (2026-05-04, PR #101)

## 배경

CustomWebService의 API 프록시(`/api/v1/proxy`)는 사용자 서비스에서 외부 API를 호출할 때 서버사이드 릴레이 역할을 한다. 이 아키텍처에서는 동일한 사용자 요청이 반복될 때마다 업스트림 외부 API 호출이 발생한다.

특히 기상청 단기예보·중기예보 API는 응답 데이터가 3~6시간 간격으로만 갱신된다. 그러나 AI가 생성한 날씨 서비스를 방문하는 사용자들이 페이지를 새로고침하거나 반복 방문할 때마다 기상청 API를 매번 호출하고 있었다. 이는 다음과 같은 문제를 유발한다:

- **불필요한 외부 API 트래픽**: 동일한 응답을 반환하는 API를 반복 호출
- **기상청 API 호출 한도 소진 위험**: 기상청 Open API는 일일·분당 호출 한도가 존재
- **응답 지연**: 업스트림 API 왕복 시간이 매번 발생 (캐시 히트 시 ~0ms vs 업스트림 ~200~500ms)

---

## 결정 사항

### 결정 1: `src/lib/cache/proxyCache.ts` 신규 모듈 (LRU+TTL 인메모리 캐시)

외부 캐시 인프라(Redis 등) 없이 단일 인스턴스에서 동작하는 인메모리 캐시를 도입한다.

**캐시 정책**:
- **알고리즘**: LRU(Least Recently Used) — 용량 초과 시 가장 오래된 미사용 항목 eviction
- **최대 항목 수**: 500개 (LRU eviction으로 초과 방지)
- **TTL 관리**: 각 항목은 `expiresAt` 타임스탬프 보유. `get()` 호출 시 만료된 항목은 `null` 반환 후 맵에서 삭제 (lazy eviction)
- **메모리 안전성**: 최대 500항목 × 평균 응답 크기(~10KB) = 최대 ~5MB 사용 예상

**캐시 키 구조**: `${apiId}:${proxyPath}:${sortedQueryParams}`
- `apiId`: API 카탈로그 식별자
- `proxyPath`: 업스트림 API 경로
- `sortedQueryParams`: query parameter를 알파벳순 정렬하여 직렬화 — `?nx=60&ny=127`과 `?ny=127&nx=60`을 동일 키로 처리
- 서버 주입 인증 파라미터(API 키 등)는 캐시 키에서 제외 — 인증 정보가 캐시 키에 포함되면 불필요한 캐시 항목 분산이 발생하고, 캐시 키 로그에 인증 정보 노출 위험이 있음

---

### 결정 2: `cache_ttl_seconds` 컬럼 (migration 020)

API별로 캐시 유효 시간을 다르게 설정하기 위해 `api_catalog` 테이블에 `cache_ttl_seconds INTEGER DEFAULT NULL` 컬럼을 추가한다.

**NULL 의미**: 캐시 비활성화. 대부분의 API는 실시간 응답이 필요하므로 기본값을 NULL로 설정하여 opt-in 방식으로 운영한다.

**초기 설정 값**:
| API | TTL |
|-----|-----|
| 기상청 단기예보 (`getUltraSrtFcst`, `getVilageFcst`) | 10800초 (3시간) |
| 기상청 중기예보 (`getMidFcst`, `getMidLandFcst`, `getMidTa`) | 21600초 (6시간) |
| 기타 모든 API | NULL (캐시 없음) |

TTL 값은 각 API의 데이터 갱신 주기를 기반으로 설정했다. 기상청은 단기예보를 약 1시간마다, 중기예보를 하루 2회 발표하므로 TTL이 갱신 주기보다 짧아 항상 최신 데이터를 제공한다.

---

### 결정 3: 캐시 적용 조건 (선택적 캐싱)

모든 요청을 캐시하지 않는다. 다음 조건을 **모두** 충족할 때만 캐시를 적용한다:

1. **HTTP 메서드**: GET 요청만 캐시. POST/PUT/DELETE 등 변경 메서드는 캐시 제외
2. **API 설정**: `cache_ttl_seconds > 0` — NULL이거나 0인 API는 캐시 비활성화
3. **업스트림 응답**: HTTP 2xx 응답만 캐시. 4xx(잘못된 요청)/5xx(서버 오류) 응답은 캐시하지 않음

**4xx/5xx 캐시 제외 이유**: 업스트림 일시 오류나 잘못된 파라미터에 대한 오류 응답을 캐시하면, 오류가 해결된 후에도 캐시 만료까지 오류 응답이 반환되는 문제 발생

---

### 결정 4: 관측성 헤더

캐시 적중 여부를 클라이언트가 확인할 수 있도록 HTTP 표준 응답 헤더를 추가한다.

- `X-Cache: HIT` — 캐시에서 응답 반환
- `X-Cache: MISS` — 업스트림 API 호출 후 응답 반환 (캐시 저장 여부 무관)
- `Cache-Control: public, max-age={ttl}` — 캐시 히트 응답 (브라우저 캐시 힌트 제공)
- `Cache-Control: no-store` — 캐시 미적용 응답

`X-Cache` 헤더는 CDN 업계 표준(Varnish, CloudFront 등)과 일관성을 유지한다.

## 선택하지 않은 대안

### Redis / Upstash
외부 캐시 서비스는 멀티 인스턴스 환경에서 캐시 일관성을 보장하지만, 현재 Railway 단일 인스턴스 배포에서는 운영 복잡성과 비용이 추가된다. 기상청 API의 캐시 특성상 재시작 후 캐시 미스가 발생해도 첫 번째 요청 이후 즉시 캐시가 채워지므로 허용 가능하다.

### HTTP 응답 헤더 기반 자동 캐시 (Cache-Control 파싱)
기상청 API 응답이 `Cache-Control` 헤더를 포함하지 않거나 `no-cache`로 설정하는 경우가 있어 신뢰성이 낮다. DB 컬럼 기반 명시적 설정이 더 예측 가능하다.

### API 카탈로그 YAML 파일에 TTL 정의
환경별 TTL 재설정이 필요하거나, 코드 배포 없이 TTL을 변경해야 하는 경우 DB 컬럼이 YAML보다 유연하다. Supabase 대시보드에서 직접 수정 가능하다.

## 결과 및 영향

### 긍정적 영향

- **기상청 API 호출 절감**: 캐시 히트 시 업스트림 호출 0회. 사용자가 많은 날씨 서비스에서 효과 두드러짐
- **응답 지연 감소**: 캐시 히트 응답은 업스트림 왕복(200~500ms) 없이 즉시 반환
- **API 한도 소진 방지**: 기상청 API의 일일 호출 한도를 캐시로 보호

### 한계 및 주의사항

- **단일 인스턴스 한계**: 인메모리 캐시는 Railway 재시작 시 초기화됨. 날씨 API 특성상(3~6시간 TTL) 재시작 직후 1회 업스트림 호출만 발생하므로 실용적으로 허용 가능. 멀티 인스턴스 전환 시 Redis 등 외부 캐시 필요
- **캐시 무효화 없음**: TTL 기반 자연 만료만 지원. 업스트림 데이터가 TTL 이전에 갱신되어도 캐시가 즉시 무효화되지 않음 (기상청 API 특성상 허용 가능)
- **500항목 용량**: 서비스 규모가 커지면 LRU eviction이 빈번해질 수 있으나, 현재 서비스 규모에서는 충분한 용량
