# 게시 사이트 프록시 오남용 모니터링 (2026-07-29)

> **언제 읽나**: siteRateLimit 프로젝트 한도 로그, GET /api/v1/admin/site-proxy-stats, SITE_PROXY_PROJECT_LIMIT_PER_MIN/IP 한도 조정, blockedByIp vs blockedByProject 해석을 손댈 때

## 상태

승인됨 — 구현 완료 ([#200](https://github.com/xzawed/CustomWebService/issues/200))

## 배경

PR #195의 site 모드는 승인된 정책에 따라 **익명 방문자도 게시 프로젝트 오너의 개인 API 키로**
업스트림을 호출할 수 있다. 게시된 사이트 자체가 공개이므로 노출 수준은 같지만,
**레이트리밋이 유일한 방어선**이 된다.

Origin/Referer 바인딩이 없어 봇이 서버에서 직접 호출할 수 있으므로 IP 버킷(20/분)은 IP를
돌리면 우회된다. **실질 상한은 프로젝트 전역 버킷(120/분)이다.**

그런데 한도 초과가 **429 응답으로만 나타나고 아무 신호도 남지 않았다.** 특정 프로젝트의 키가
소진되고 있어도 오너도 운영자도 알 수 없었다. 기본값 20/120도 게시 사이트 실사용 데이터가
없는 상태에서 보수적으로 정한 값이라, 정상 트래픽을 막고 있는지 과도하게 허용하고 있는지
판단할 근거가 없었다.

## 결정

### 1. 프로젝트 전역 한도 소진 경고

`checkSiteRateLimit`에서 프로젝트 버킷이 한도에 도달하면 `logger.warn`을 남긴다.

**버킷당 윈도 1회로 억제한다.** 봇이 계속 두드리면 매 요청마다 남아 로그가 무의미해진다.
억제 플래그를 버킷에 붙였으므로 윈도가 새로 열리면 자연히 다시 경고한다 — 지속되는 소진은
계속 보여야 하기 때문이다.

**IP 한도 초과는 경고하지 않는다.** 한 방문자의 과속은 오남용 신호가 아니고, 정상 트래픽에서도
나온다. 경고를 붙이면 실제 신호가 묻힌다.

전체 버킷 용량이 소진되어 버킷조차 만들지 못한 경우는 별도 경고를 남긴다(억제할 버킷이 없으므로
시간 기반으로 억제).

### 2. 운영 지표 — `GET /api/v1/admin/site-proxy-stats`

프로젝트별 누적 집계를 `ADMIN_API_KEY` 보호 엔드포인트로 노출한다.

| 필드 | 의미 |
|------|------|
| `allowed` | 통과한 호출 수 |
| `blockedByIp` | IP+projectId 버킷(20/분)에 걸린 횟수 |
| `blockedByProject` | **프로젝트 전역 버킷(120/분)** 에 걸린 횟수 — 0이 아니면 오남용 또는 한도 부족 |

**두 차단을 구분해 센다.** 합쳐 놓으면 "429가 많다"는 것만 알 뿐 *어느 경계가 물렸는지* 모르고,
그러면 어느 값을 조정해야 하는지도 알 수 없다.

집계는 리밋 버킷과 달리 **윈도가 지나도 누적된다** — 순간 상태가 아니라 추세를 봐야 하기 때문이다.
현재 한도 설정(`limits`)도 함께 반환한다. 수치만 보면 조정 판단을 할 수 없다.

### 3. 절단은 드러낸다

- 추적 용량(`MAX_SITE_RATE_LIMIT_BUCKETS`)을 넘기면 **새 프로젝트만** 집계에서 빼고 기존
  카운터는 계속 센다. 빠진 사실은 `truncated: true`로 알린다.
- `?limit=N`으로 상위 N개만 받을 때 `trackedProjects`(전체)와 `returnedProjects`(반환)를
  함께 준다.

조용히 자르면 "이게 전부"로 오독된다.

## 하지 않은 것

### Slack 승격 — 보류

이슈는 `sendSlackAlert` 승격을 "검토"로 제안했다. 지금은 하지 않는다:

- `SLACK_WEBHOOK_URL`이 프로덕션에 미설정이라 승격해도 no-op다(테스트 불가)
- **경보 임계를 정할 트래픽 데이터가 없다.** 임계 없이 붙이면 정확히 이슈가 경고한
  경보 피로를 만든다

먼저 로그로 관측하고, 실사용 패턴이 보이면 임계·중복 억제를 설계해 붙인다.

### Origin/Referer 바인딩 — 보류

이슈도 "도입 전 실제 트래픽 패턴을 먼저 볼 것"이라 명시했다. 헤더는 위조 가능해 단독 경계가
될 수 없고, 정상 요청(브라우저 확장·프라이버시 설정)을 막을 위험이 있다. 이번 지표가 쌓인 뒤
판단한다.

### 기본값 20/120 조정 — 데이터 없음, 재검토 절차만 고정

**아직 조정하지 않는다.** 판단 근거가 될 실사용 데이터가 없기 때문이다(2026-07-29 기준 게시
사이트는 검증용 1개뿐). 환경변수라 코드 변경 없이 조정할 수 있다.

재검토 기준을 여기에 고정한다:

| 관측 | 해석 | 조치 |
|------|------|------|
| `blockedByProject > 0`가 정상 사이트에서 반복 | 한도가 실사용을 막고 있다 | `SITE_PROXY_PROJECT_LIMIT_PER_MIN` 상향 |
| `blockedByProject`가 특정 프로젝트에만 대량 | 오남용 또는 생성 JS의 과도한 폴링 | 해당 프로젝트 조사 — 키 소진 여부 확인 |
| `blockedByIp`만 많고 `blockedByProject`는 0 | 소수 방문자의 과속 | 정상. IP 한도만 소폭 상향 검토 |
| 전 프로젝트에서 차단 0 | 한도가 느슨하거나 트래픽이 적다 | 유지 (하향은 근거 부족) |

## 트레이드오프

**집계는 인메모리라 재시작 시 사라진다.** 레이트리밋 자체와 동일한 단일 인스턴스 전제다.
DB에 쌓으면 영속되지만 매 프록시 요청마다 쓰기가 생겨 핫 패스에 비용이 붙는다. 지금 필요한
것은 "며칠 관측해 한도를 조정할 수 있는 정도"이므로 인메모리로 충분하다. 응답의 `since`·`note`가
이 성질을 드러내 수치를 오독하지 않게 한다.

## 검증

TDD로 작성했고 신규 테스트가 구현 전에 실패하는 것을 확인했다.

| 항목 | 결과 |
|------|------|
| `pnpm test` | 전체 통과 |
| `pnpm type-check` | 통과 |
| `pnpm lint` | 0 errors |
| `pnpm build` | 통과 |

고정한 것:

- **경고** — 프로젝트 한도 도달 시 1건, 같은 윈도 반복 초과에도 1건(억제), 새 윈도에서 재발생,
  IP 한도 초과는 경고 없음, 프로젝트별 독립
- **집계** — 프로젝트별 허용 수, IP 차단과 프로젝트 차단의 구분, 윈도를 넘겨 누적,
  용량 초과 시 `truncated`, 리셋 시 초기화
- **엔드포인트** — 403(키 없음·틀림), 호출량 내림차순, `limit` 적용 시 전체 개수 보고,
  잘못된 `limit` 폴백, 호출 없을 때 빈 목록(500 아님), 인메모리임을 응답에 명시
