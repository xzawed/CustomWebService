# 프록시 캐시 키에 키 신원 추가 (2026-07-29)

## 상태

승인됨 — 구현 완료 ([#199](https://github.com/xzawed/CustomWebService/issues/199))

## 배경

`buildCacheKey`는 `apiId:proxyPath:params`뿐이라 **어떤 키로 받은 응답인지**가 캐시 키에
들어가지 않았다. 그런데 프록시는 프로젝트 오너의 **개인 API 키**를 주입할 수 있다. 키가
다르면 응답도 다를 수 있으므로(사용자별 쿼터·개인화 데이터) 같은 캐시 항목을 테넌트 간에
공유하면 유출이 된다.

PR #195에서 익명 site 모드가 도입되며 **익명 호출자가 오너 키로 업스트림을 호출**하게 되어
이 위험이 잠복에서 실재로 바뀌었고, 급한 대로 **개인 키 응답은 캐시를 통째로 건너뛰는**
가드레일을 넣었다. 안전했지만 근본 설계는 그대로였고, 키 의존 API는 캐시 이득을 전혀 받지 못했다.

현재 활성 카탈로그 36개는 대부분 키리스라 체감 영향이 없지만, 키-게이팅된 24개 API를
재활성화하면 그 API들의 업스트림 호출량과 오너 키 쿼터 소진이 그만큼 늘어난다.

## 결정

**캐시 키에 주입된 키의 지문을 넣는다**(이슈의 방안 A).

```ts
`${apiId}:${proxyPath}:${sortedParams}:${keyIdentity}`
```

`keyIdentity`는 실제로 **주입된 값**의 `sha256` 앞 16자, 주입이 없으면 `'none'`이다.

### 원문이 아니라 지문인 이유

캐시 키는 로그·디버깅 경로에서 보일 수 있다. 원문을 넣으면 키가 그대로 새어 나간다.
16자로 자르면 길이 정보도 남지 않는다(충돌 확률은 64비트라 캐시 용도에 충분하다).

지문은 로그·응답 헤더·에러 메시지 어디에도 노출하지 않는다 — 캐시 키 문자열 안에서만 쓰인다.

### 4번째 인자를 선택 인자로 두지 않은 이유

`keyIdentity`는 **필수 인자**다. 선택으로 두면 호출부가 잊었을 때 조용히 예전 위험이
돌아온다. 필수로 두면 새 호출부가 반드시 "이 요청의 키 신원은 무엇인가"를 답하게 된다.

### 플랫폼 키도 지문을 쓴다

이슈는 플랫폼 키를 `'platform'` 리터럴로 고정하자고 제안했지만, 실제 값의 지문을 쓴다.
값이 같으므로 **모든 호출자가 캐시를 공유하는 동작은 동일**하고, 여기에 더해 키를 교체하면
지문이 바뀌어 **옛 키로 받은 응답이 자동으로 무효화**된다.

### 주입 여부까지 반영

`resolvedKey`가 있어도 `cfg.param_name`이 없으면 실제 주입은 일어나지 않는다. 그 경우
`'none'`을 쓴다 — 그러지 않으면 키가 주입되지 않은 응답이 주입된 응답과 같은 항목을 쓴다.

### 가드레일 제거

`usedPersonalKey`로 캐시를 건너뛰던 분기를 없앴다. 격리는 이제 캐시 키가 담당한다.
`usedPersonalKey` 자체도 다른 소비처가 없어 함께 제거했다.

## 남는 성질 (변하지 않음)

**응답 본문은 여전히 프로세스 메모리에 평문으로 남는다.** 키별 격리와는 별개 문제이고
플랫폼 키 응답에도 동일하게 해당한다. 캐시는 카탈로그에 `cacheTtlSeconds`가 명시된 API에만
활성화되므로 **무엇이 캐시되는지는 관리자의 명시적 결정**이다. 민감 데이터를 반환하는 API에
TTL을 부여할 때는 카탈로그에 캐시 민감도 플래그를 두어 제외하거나 at-rest 암호화를 적용할 것
(이슈의 방안 B). `proxyCache.ts` 주석에 그대로 남겼다.

## 검증

TDD로 작성했고 신규 테스트가 구현 전에 실패하는 것을 확인했다.

| 항목 | 결과 |
|------|------|
| `pnpm test` | 전체 통과 |
| `pnpm type-check` | 통과 |
| `pnpm lint` | 0 errors |
| `pnpm build` | 통과 |

고정한 것:

- **격리** — 서로 다른 개인 키로 받은 응답이 캐시를 공유하지 않는다(라우트 레벨에서 업스트림
  2회 호출·둘 다 `X-Cache: MISS`로 확인)
- **효율 회복** — 같은 키를 쓰는 두 요청은 캐시를 공유한다(업스트림 1회)
- **키 없음 vs 있음** — `'none'`과 지문은 절대 충돌하지 않는다(`'none'`은 16자 hex가 아니다)
- **지문 성질** — 결정적, 원문 미포함, 입력 길이와 무관하게 16자 hex
- **회귀 없음** — 플랫폼/키리스 경로의 기존 캐시 동작(MISS→HIT, `no-store`, POST 미캐시) 유지
